# Учебный набор регрессионных проверок Wazuh
Для уроков17.01 и17.03. Синтетические данные, не копия производственных журналов.

## 1. Проверить формат на любом компьютере с Python3
```bash
python3 check_fixtures.py
```
Это проверяет JSON/XML и согласованность manifest, но не совпадение правил.

## 2. Подготовить собственный изолированный менеджер
Сначала прочитайте XML и Python. Проверьте, что ID100700,100710,100711 свободны.
Сохраните текущие пользовательские файлы. Скопируйте course_auth_rules.xml
в /var/ossec/etc/rules/ без перезаписи существующего файла.
Не изменяйте поставляемый /var/ossec/ruleset/rules/.
Проверьте sudo /var/ossec/bin/wazuh-analysisd -t.
Существующие конфликтующие или более специфичные правила могут изменить
конечный результат. Не подгоняйте manifest без изменения контракта.

## 3. Запустить настоящий движок
```bash
sudo python3 run_logtests.py
```
Ожидаются6PASS. Ненулевой статус любого образца означаетFAIL,
включая отрицательные примеры: для них ожидается точное benign/base-правило.
Проверьте чувствительность: в копии manifest измените ожидаемый уровень failed
на6. Набор обязан завершитьсяFAIL. После проверки восстановите оригинал.

Код не перезапускает менеджер и не добавляет события агенту. Для проверки
реального потока нужны штатное применение конфигурации и новая запись
с уникальным request_id, как описано в уроке17.01.
Корреляцию проверяют отдельной последовательностью в одной logtest-сессии;
однострочные -U процессы не доказывают frequency/timeframe.
Реальный Wazuh здесь автоматически не разворачивается. Не используйте
непроверенный pull request на runner с доступом к производственной системе.
